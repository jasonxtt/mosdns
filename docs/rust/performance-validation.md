# Rust-native 性能与稳定性验收方案

规划日期：2026-09-20。适用范围：Linux amd64，Phase 5A–6。
这是待实施的验收方法，不是已运行的 benchmark、已通过的 gate 或新的性能承诺。
架构和阶段定义见 [重写方案](../ai/rust-rewrite-plan.md)，功能范围见 [覆盖总表](feature-coverage.md)。

## 1. 成功的定义

完整功能、正确 DNS/路由结果和稳定运行是前提。优先改善查询延迟、满足延迟和错误率要求时的持续有效吞吐、故障后的恢复；CPU 效率和有界内存是资源指标。没有要求内存必须下降某个比例。

不能仅以最大并发任务数或峰值 QPS 验收。NXDOMAIN、策略拒绝等按配置预期的响应可以是正确结果；上游故障造成的非预期 SERVFAIL、错误回答、超时及丢包必须分类计数，不能计入正常负载的成功吞吐。故障场景另按其预先定义的期望行为判定。

## 2. 基线与可复现环境

- 比较独立 Go-only 和 Rust-native release 进程；固定并记录各自 commit、工具链、构建 flags、依赖锁文件、CPU 架构选项、Linux/kernel、CPU 配额/亲和性、可用内存及文件描述符限制。
- 冻结 Go 参考版本和 config-package 版本/哈希；记录 workload、脱敏配置、规则数据集哈希、缓存容量/TTL、审计与日志设置、协议及并发设置。main 同步后的契约变化应更新基线及覆盖表，不能无限移动验收目标。
- Go 使用合理且公开的运行参数，记录 GOGC/GOMEMLIMIT/GOMAXPROCS 等；不得故意压低某一实现资源或只单边调优而不说明。
- 使用相同请求集、缓存预热与生命周期设置。设置容量相同不意味着命中率相同；必须同时报告命中率、淘汰和内存，不能靠减小缓存、降低规则规模、关闭审计取得收益。
- 首先使用可控本地/局域网 upstream，隔离网络随机性；再用真实配置的脱敏流量分布和外部网络验证实际效果。缓存命中、受控未命中和公网结果分别报告，不能混成语言性能结论。
- 负载机和模拟上游必须留有余量，记录各方 CPU 和发送能力；若共机运行则隔离资源并披露干扰。发生负载机限速时，该结果不能作为被测服务的容量上限。
- 每个关键场景预热后至少重复三次，交错 Go/Rust 顺序，保存全部样本与环境噪声。报告分布及波动；结果接近噪声时增加样本或标为不确定，不挑选最好一轮。
- 早期 Go/cgo 的 B/op 不涵盖 Rust 堆，hybrid RSS 也不等于独立 Rust 进程。现有 cache/matcher 记录只作历史证据，不换算成 native 收益。

## 3. 指标与负载生成

| 指标 | 测量和判定方法 |
| --- | --- |
| 正确性 | 对响应和路由/审计做契约校验；对 ID、时间、TTL 等动态字段仅按明确规则归一化，不屏蔽语义差异。 |
| 延迟 | 客户端记录 p50/p95/p99；样本量足够时另报 p99.9。记录发送计划、实际发送、收到响应时间和排队影响；超时不能从报告中删除。 |
| 有效吞吐 | 同时记录 offered QPS、实际发送、总响应、正确且按期完成数量、错误/超时/丢包。容量是满足预冻结预算的最高可持续负载。 |
| 并发扩展 | 在相同 CPU/连接/请求预算下扫描并发度和请求速率，观察吞吐、尾延迟及锁/调度热点，不能把任务数量当处理能力。 |
| CPU | 进程 user+system CPU、每个有效查询的 CPU 时间；结合 profiling 定位解析、复制、锁、调度和 syscall 成本。 |
| 内存与资源 | 独立进程稳定/峰值 RSS，必要时 PSS 和 allocator 数据；连接、FD、后台任务、队列深度及超时工作回收趋势。RSS 不返回初始值不单独等同泄漏，需区分分配器保留与活跃资源增长。 |
| 恢复能力 | 从故障解除到有效吞吐/延迟回到预定义正常区间的时间，以及资源回收时间、残留连接/任务和是否需要重启。 |

优先采用独立于响应速度的固定发送速率扫描（低负载 -> 常用负载 -> 接近饱和 -> 过载 -> 恢复）。客户端发不出来的请求另记，不能因服务变慢导致压测自动降速后声称延迟稳定。闭环压测可作补充，须标注方法，不能替代上述容量和尾延迟证据。

正常场景和过载场景的延迟、丢弃/拒绝、超时分别展示；不得从大量失败中挑出少量快速响应来宣称 p99 优秀。请求标识、问题、返回数据需校验，防止重复/串包被计入吞吐。

## 4. 工作负载矩阵

| 场景 | 主要变体与期望 | 归属 |
| --- | --- | --- |
| 缓存命中 | 热点/均匀分布、正/负响应、不同报文大小、ECS 隔离、lazy TTL；验证 TTL/ID/命中率 | 5A 起，5B 补全 |
| 未命中与混合流量 | 受控 upstream 延迟、小/大响应、TC→TCP、命中比例变化、真实分布回放 | 5A 起，5B 补全 |
| 规则匹配 | 真实规模及扩展规模的域名/IP/正则/keyword、优先级、special_groups、不同分支深度 | 5A 起，5B/5C 补全 |
| 传输与连接 | UDP/TCP/DoT/DoH(H1/H2)/DoQ/DoH3，冷握手与热复用分别测；混合协议与并发隔离 | 剩余 Phase 4 + 5B |
| 慢上游与失效 | 超时、断连、拒绝、错误包、单上游和多上游故障；bootstrap/连接恢复、fallback；记录放大的上游请求数 | 5A 基础，5B 完整 |
| 过载与取消 | 突发/持续过载、队列满、连接/stream 限额、期限过期、客户端取消；恢复后无残留工作持续占用资源 | 5A 起，5D 完整 |
| 管理并发 | 查询期间下载规则、编译/切换快照、保存配置、访问统计/日志和 dump；失败回滚与旧快照回收 | 5C/5D |
| 生命周期 | 正常停止、失败初始化清理、更新失败、重启恢复；保存文件/状态一致性和重新服务 | 5A 基础，5C/5D 完整 |
| 非法输入 | DNS 压缩/长度边界、截断流、配置引用错误；按契约拒绝且不污染缓存或其他查询 | 各拥有模块 + host E2E |
| 长期运行 | 持续查询、周期 reload/故障/恢复，观察内存/FD/任务增长和响应退化 | 5D，Phase 6 回归 |

短 loopback 测试、几秒 benchmark 或仅模型测试不能替代长期运行。5D 任务必须在执行前规定 soak 时长、采样频率、reload/故障循环次数和恢复期限；建议至少覆盖一个完整日周期，具体预算由任务基于运行场景冻结。

## 5. 验收阈值如何冻结

当前没有完整 native baseline，不虚构“快 30%”或固定 QPS 承诺。按以下顺序推进：

1. 在 5A 建立 Go 基线和最小 native 链路，固定代表性 workload 与测量方法，明确环境噪声和初步瓶颈。
2. 在各任务进入性能验收前，将适用 workload 的 p95/p99 上限、正确/按期响应率、目标 offered QPS 或容量、CPU/内存/队列预算、恢复期限及允许波动写入该任务的 `prd.md`/`implement.md`。不能测完候选才放宽标准。
3. 子集测量只对相同子集有效；5D 使用 5B/5C 功能完整、审计等开关一致的 Go/Rust 配置，并在最终候选测量前冻结综合阈值。
4. 默认要求关键负载无超出测量波动的实质退步，性能改进要有可重复证据；若结果仅持平，应明确写“完成重写，未证明性能提升”，不能宣称已实现性能目标。进一步接受何种取舍需基于具体证据由用户决定。
5. 内存无需必然降低，但增长必须有上限、回收证据及收益说明，不能靠无限队列或无限缓存支撑性能。重大延迟/吞吐/稳定性退步不能以省内存抵消。
6. 功能缺失、错误响应、不可恢复的资源增长或残留后台任务属于阻塞，不得由高 QPS 抵消。

历史 Phase 1 的 10% hybrid 门槛及失败结论原样保留；上述 native 预算不是重写历史报告或绕过正确性门禁的理由。

## 6. 证据交付与发布

每份报告必须包含源码/配置/数据集标识、构建及运行命令、环境、预冻结阈值、所有原始结果位置、失败计数、对照汇总、适用范围和未覆盖项。profiling 的解释应区分已证明原因与待验证假设。

从 5A 起每批集成维护趋势；5D 完整验收后，Phase 6 清理 hybrid 构建/运行依赖，并重跑完整 E2E、性能和稳定性 gate。先本地构建验证，再在隔离 `mos-test` 使用专用目录/端口验证；生产 `mosdns` 替换仍需用户明确确认。保留可执行回退方案，包含旧二进制、配置/状态备份及格式兼容检查。
