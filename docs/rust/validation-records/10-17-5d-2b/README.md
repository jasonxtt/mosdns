## L：32 000 qps 冷启动 `late_wrong` 诊断（5D-1 发送器不变，保留每个错误/迟到应答的完整内容；原生 ×3 + 附加运行，Go ×1 + 附加运行）

- 原生：3 次分别出现 175/162/134 个 `late_wrong`（960 000 个计划查询中的 0.014–0.018%），**全部**是格式正确的 SERVFAIL（rcode 2、问题段正确、无答案记录），
  **没有一个是错误的答案内容**（`answer_differs`=0、`question_differs`=0、`ttl`=0）。全部只出现在 32 000 qps 档位的开头约 0.3 s（冷缓存突发），
  全部是 domestic 组的名字，且全部在计划时刻之后 5.00–5.02 s 返回，即请求期限（5.0 s）到期。
  64 000 qps 档位没有 `late_wrong`（那里的失败为超时/未发送）。Go：0 个 `late_wrong`，但有 470 个 `late_correct`（迟到但正确）。
- 已证实的事实：被拒绝的应答都是上述 SERVFAIL；这些名字每个都在 mock 的日志里出现两次（domestic 组有两路上游，两路都送到了 mock），
  但 mock 看到它们的时刻比计划时刻晚 0.1–1.0 s（正常查询几乎同时）——模拟上游（单进程 Python）在冷启动突发里已经饱和；mock 自己的 UDP socket（端口 15000）在每次运行里丢了数据报
  （原生运行 440/535 个，Go 运行 1781/1073 个）。**原生一侧没有丢包**：附加运行里命名空间的 `RcvbufErrors` 总数（637 314）恰好等于 53 端口 socket（636 779）加 mock 端口（535），
  即使原生为每次上游调用新绑定、随后关闭的短命 socket 也计在命名空间总数里，所以它们没有任何丢包。
- **未能证实的部分：** 为什么这些查询已经送到 mock（两路都到），却一直等不到可用应答直到 5.0 s 期限。我没有证据区分“mock 在饱和期间应答很晚/没有应答”与“原生没来得及消费已到的应答”；
  mock 不记录应答，原生也没有逐请求的上游事件。此外，原生的附加运行里 `NoPorts`=3877（应答到达时调用的 socket 已关闭，两路竞速里输掉的一路的正常现象或迟到应答），Go 为 0。
  现有证据支持的结论只有：这是过载下“在期限处 SERVFAIL”的失败方式，没有任何答案内容错误、也没有串话迹象；它与 mock 的饱和同时出现，但因果关系**没有被证实**；若需要彻底定因，需要原生逐请求上游事件或应答时间戳的插桩，不在本任务范围。
  附加运行原生 `late_wrong` 为 218（种子 501）与 263（种子 502），Go 均为 0，量级一致。

## 注入证据与审查后加强的判定

Codex 第 1 轮指出若干判定可能“空转”，据此加强并对所有已保留数据重新判定（`scenarios.py --reanalyze`，原结果保留为每个运行目录里的 `result-v1.json`），F3 因回查名字的选取方式改变而重新运行（原 F3 运行保留在 `runs/`，新运行在 `runs-f3b/`）：
- `fault_took_effect_as_seen_by_the_mock`：每个注入的故障表必须出现在 mock 的 journal 里（mock 真的应用了它），并且 mock 的计数证明它命中了流量——`<组>:<协议>:fault:<模式>` 计数，`handshake_reset` 计数，SOCKS 的 `fault:blackhole` 计数，
  或（拒绝监听/代理 down）基线有新连接而故障窗口内为零。Go 参考持久连接、基线没有新连接时无法用“沉默”证明，只要求 journal 与其它计数；原生必须全部成立。原生 F1–F5 全部成立。
- F3 的回查名字均匀分布在整个故障期，四个故障段（bad_id/truncated/wrong_question/servfail）每段每组至少 50 个（实测 75 个）。
- F6：mock 依序服务六种响应，日志恰好 5 条且各自的原因对应；成功下载后规则文件被改写。H2 同样检查每次刷新 mock 都服务了一次成功响应，规则文件被改写。
- 所有 H：计划的管理请求必须全部执行且返回 2xx（异常结果不再被忽略）；H4 的窗口从任务启动到完成后 1 s，并要求 wrong 答案逐个满足“问题段一致、NOERROR、地址在 mock 发出的集合内”。

逐次运行的清理后摘要（只含状态计数、判定、恢复秒数、RSS 峰值、UDP drops，不含名字）见 `run-summary.json`：`runs` 是 55 次原计划运行（其中的 4 次旧 F3 用旧判定，仍保留），`runs-f3b` 是加强回查后的 4 次 F3，`runs-ref` 是 Go 的 H1/H2/H3 参考；
前者经重新判定的结果为当前判定（F3 除外，它的旧回查名字不满足新的覆盖检查）。Codex 共 3 轮：第 1 轮 7 项 P1，第 2 轮核对后遗留 1 项（H4 的及时 SERVFAIL 可通过），第 3 轮 `NO P1` / `FINAL: PASS`。

## 发现

1. **（需要决定）热应用会阻塞 DNS 线程约 0.5–0.65 s，500 qps 下会因内核 UDP 缓冲溢出丢查询。** H1 每个窗口丢 6–93 个，H3 0–42 个；100/250 qps 不丢但约 1% 的查询晚到 0.5–0.65 s。Go 参考在 H1 零丢失、H2 零丢失。
   选项：（a）为 UDP 监听设置更大的 `SO_RCVBUF`（小改动，`bind.rs`/`udp.rs`；只缓解丢包，查询仍晚到约 0.6 s，且受内核 `rmem_max` 限制）；（b）把候选配置的编译移出 DNS 线程（根治，改动较大，不在本任务内）；（c）接受并在运维文档里注明。
2. **H3 Go 参考丢得更多**（每个窗口 630/728 个），说明专用组保存本来就是带短暂中断的操作；原生丢得少，且仅在高负载时。
3. **F5：foreign DoH 对 2 s 慢速 HTTP/1.1 上游时，原生约 83% 的 foreign 查询在 5 s 期限 SERVFAIL（Go 全部在 2.0 s 正确）。** 原因与 5D-fix-A 的设计一致：HTTP/1.1 连接池上限 12（`MAX_DOH_CONNECTIONS`），
   每个连接一次只处理一个请求；100 qps × 2 s 需要 ≈200 个并发连接。真实 DoH 服务器用 h2 多路复用（`MAX_DOH_STREAMS`），不受这个上限影响；本测试的 mock 只会 HTTP/1.1。回退（`fb`）行为不受影响。仅报告。
4. **故障之后 RSS 不回落：** F1/F3/F5 在故障窗口后 RSS 从约 47 MiB 升到 63–80 MiB 并保持（FD、线程回到基线），应是堆高水位而不是持续增长（最终观察段是平的）；但我没有做长时间重复故障来证明不泄漏，这属于 5D-3 范围。
5. **Go 参考的两处行为差异（不影响原生判定）：** F3 中 Go 会把 `wrong_question` 的应答原样转发（399/548 个错误答案）并把它们留在缓存里（149/600 个重新查询仍错），原生拒绝并 SERVFAIL、缓存不受影响；F4b 中 Go 的 FD 持续增长且不恢复。均不要求原生向 Go 看齐。
6. 验证方法上的注意：H4 的 requery 会 flush 缓存，所以与任务前 oracle 的差异只能在任务启动之后出现；Go 参考需要把其 API 端口改为配置里写的 9099 才能运行同一任务。
