## A. 已删除专用组产物清理失败不再停 DNS
- 行为：提交并退休旧代后，对孤儿产物（槽位 >= 50 且不是当前活动组）做一次清扫；失败只告警，并列入 `GET /api/v1/system/health` 的 `pending_cleanup`
  （相对配置根目录的路径，正常为 `[]`，不影响 `ready`/状态码）。每次后续的组保存与每次启动再清扫一次，故障消除后自动清空；新组占用的槽位文件不会被清扫。
  启动时的孤儿清理失败同样只告警并继续启动（状态不一致、派生 YAML 写入失败仍然是启动错误）。
- 不变：提交边界；旧代退休失败、托管 store 收尾失败等其它 `CommittedCleanup` 仍使 host 进入 recovery_required 并停止。
- 测试（`tests/m1_e_standard_groups.rs`）：让被删组的 `rule/special_50.txt` 变成非空目录（`remove_file` 必败）→ `DELETE` 返回 204、health 仍 200/`ready:true` 且
  `pending_cleanup == ["rule/special_50.txt"]`、DNS 照常应答、组确已删除；故障消除后下一次保存重试，新组占用槽位 50 时其文件保留，再删除后文件被清除、清单为空；
  启动时一个可删孤儿被删除、一个不可删孤儿（目录）使启动继续并出现在 health。

## B. 深嵌套延迟分支空转
- 测试（`execution.rs`，N 层嵌套 `fallback`，最内层主分支的上游等待 200 ms，统计最外层 future 的轮询次数）：

| | 4 层 200 ms | 40 层 200 ms | 40 层 600 ms | 40 层取消测试（150 ms 后取消） |
| --- | --- | --- | --- | --- |
| 修复前（`pump` 无条件 `wake_by_ref`） | 2 | **9076–10036** | **26212–32720** | 5975（断言 < 400 失败） |
| 修复后 | 2 | **20** | **20** | < 400，且在 5 s 内结束 |

  修复前的次数随等待时间线性增长（忙轮询占满唯一的 CPU）；两次修复前运行的绝对值不同是因为计数取决于调度节奏，数量级与线性关系一致。
- 根因：嵌套 >= 16 层时，第 16 层任务每次外层轮询都被重新延后；`pump` 轮询它并无条件唤醒外层；最后被轮询的叶子只是在等 I/O，但那次唤醒又触发下一轮重新延后，循环不会自行结束。
- 修复：`pump` 只在刚轮询的分支已完成（外层要消费结果）或仍有延后任务待续时才唤醒外层；等待上游的分支由上游的 waker 唤醒。祖先顺序、弱引用所有权、根预算/取消/期限规则未改。
- 既有的 32 层主优先、重定向环栈保护、fallback 相关测试全部通过；新增取消测试证明深层分支仍在取消后结束（取消经 `TransportCancellation` 传给上游唤醒，不依赖忙轮询）。
