# Native online update, automatic rollback and configuration package (F-3a)

Status: implemented in `rust/native-host/src/update/`. Validation: [10-18-f3a](../validation-records/10-18-f3a/README.md).
Design notes and the Go comparison: the task's `research/design.md` / `go-semantics.md`.

## Scope and decisions (user, 2026-10-18)
- Releases stay in `jasonxtt/mosdns`; the Rust program uses its own tag prefix **`rust-v`** (`rust-v0.1.0`). Only `rust-vX.Y.Z` tags are considered (not draft, not prerelease); the Go `v…`/`lite-v…` releases are ignored. Linux amd64 only (`architecture: "linux/amd64"`; other platforms report the capability as unsupported).
- An upgrade is the program plus, when the release needs a newer one, the `config_rust` package. The UI is built into the program, external UI packages are not part of an upgrade.
- A failed upgrade is rolled back automatically; this must not depend on `systemd` (the production unit is `Restart=always`, `RestartSec=2min`).
- The first switch from Go to Rust is a deployment script (F-3b), not this feature.

## Versions
`mosdns version` and `GET /api/v1/system/health` `version` print the build version: the release tag (`MOSDNS_BUILD_VERSION=rust-vX.Y.Z`), or `rust-v<crate version>` for any other build. An update is *available* only when the release is strictly newer (Go also counts downgrades); `force` reinstalls.

## HTTP API (WebUI `/`)
| Route | Behaviour |
| --- | --- |
| `GET /api/v1/update/status` | Within 3 s, from a 15-minute cache. A failed check is still `200` with `message: "检查更新失败：…"`. |
| `POST /api/v1/update/check` | Forces a check (8 s). Same degraded answer on failure. |
| `POST /api/v1/update/apply` | Optional body `{"force": bool, "prefer_v3": bool}` (`prefer_v3` is accepted and ignored). Bad body `400 {"error"}`; nothing newer and not forced `200 {status, installed:false, restart_required:false}`; any refusal `502 {"error"}` (`409` while another update or restart is running, `501` where updating is unsupported); success `200 {status, installed:false, restart_required:true, notes}` with `status.pending_restart: true`. |
| `POST /api/v1/config/export` | Body `{"dir"}` → `application/zip`, `Content-Disposition: attachment; filename="mosdns_backup_<unix>.zip"`. Missing `dir` → `400 dir is required`; undecodable body → `400 Invalid request body` (plain text). |
| `POST /api/v1/config/update_from_url` | Body `{"url","dir"}` (`400 url and dir are required` / `Invalid request body`). Success `200 {"message":"Update successful. N files will be updated. Restarting...","status":"success"}`; the change is applied by the guard (below), so it is rolled back automatically if the host does not come up. |
Other methods are `405`. `UpdateStatus` has Go's fields (`current_version`, `latest_version`, `release_url`, `architecture`, `asset_name`, `download_url`, `asset_signature`, `current_signature`, `published_at`, `checked_at`, `cache_expires_at`, `update_available`, `cached`, `config_schema_required`, `config_schema_applied`, `config_update_status/_message/_error/_backup`, `config_package_id`, `message`, `pending_restart`, `rollback_performed`, `rollback_message`; empty optional fields are omitted). Not applicable here: `amd64_v3_capable`/`current_is_v3` (no GOAMD64 levels), `config_auto_updated` (always 0: the guard applies the package).
Differences from Go, all on purpose: **only this host's own configuration directory** is exported or replaced (`dir` must be the real configuration root; Go reads/overwrites any directory the client names); `update_from_url` accepts only a valid configuration package (manifest, sha256 per file, managed paths), not an arbitrary zip; the export leaves out `backup/` and `update/` and does not follow symbolic links, with a 128 MiB limit and **one export at a time** (a second one gets `503 another export is in progress` until the first response has been written), because each is built in memory; downloads are size- and time-bounded.
Capabilities `system.update` / `system.config_management` are *supported* when the platform is linux/amd64 (update only), the host has a configuration root, and the process captured its executable path; otherwise they report why. `GET /api/v1/system/health` shows `required_config_schema`, `applied_config_schema`, `config_management_enabled` and `update: {state: idle|pending|rolled_back, …}` (never affects `ready`).

## Release layout
- `mosdns-rust-linux-amd64.tar.gz` (one file named `mosdns`), `mosdns-rust-update-manifest.json` (`format 1`, `channel "rust"`, `version`, `required_config_schema`, `config_package_id`, `artifacts{name:{sha256}}`, optional `config{url,sha256}`; unknown fields are refused). The release listing is read from `https://api.github.com/repos/jasonxtt/mosdns/releases?per_page=100` (`MOSDNS_UPDATE_API_URL` replaces it for tests or mirrors; nothing skips the sha256 checks). Downloads use the configured `socks5_proxy` object (then directly if the proxy fails).
- `scripts/build-rust-release.sh rust-vX.Y.Z` builds the artifacts and `scripts/generate-rust-update-manifest.sh` the manifest (it refuses when `scripts/rust-release-metadata.json` and the constants in `update/mod.rs` disagree). Nothing is published by these scripts.
- Configuration package `config_rust_up.zip` (built by `file/mosdns/config/build_config_rust_up.sh`): `manifest.json` + the managed files, `channel "rust"`, `config_schema`, `package_id`. Managed: `config_custom.yaml` and `sub_config/*.yaml` except the host-generated `special_groups.yaml`; `create_if_missing` only `rule/switchN.txt` (`A`/`B`); `delete_files` only `sub_config/*.yaml`. The program requires `REQUIRED_CONFIG_SCHEMA = 1` / `REQUIRED_CONFIG_PACKAGE_ID = "rust-config-schema-1"`; binary-only releases leave them unchanged and a structural change of the managed files bumps both. The package state is **`webinfo/rust_config_update_state.json`** — never the Go host's `config_update_state.json`.

## Safety rules (all enforced, all tested)
1. The program asset's sha256 must equal the manifest's; the package's sha256 must equal the manifest's and every managed file must match the package manifest; the candidate must report exactly the release tag (`candidate version`); a mismatch anywhere stops before anything is changed.
2. Before the service is touched, the candidate is run against the *new* configuration (`candidate check` on a scratch root built from links and the package's files): a program or package the new program rejects fails the request with the reason, and DNS never notices.
3. Only managed files are written (never the host-generated `sub_config/special_groups.yaml`, neither as a managed file nor in `delete_files`); every target is refused if it is reached through a symbolic link; each file is replaced atomically and durably (temporary file, fsync, rename, directory fsync) and each deletion is made durable by a directory fsync as well.
4. The old program, the old managed files and the old package state are saved in `<root>/update/txn-*/` **before** anything changes, and the directory entries leading to the transaction (`update/`, the configuration root) are flushed before the guard starts. A program update is refused up front when the program's own directory cannot take a new file (installing and rolling back both need it).

## Transaction and rollback
States: `staged` → `installing` → `testing` → `verified`, or `rolled_back` (file `update/txn-*/transaction.json`).
1. **Stage** (in the running host): downloads and checks as above, writes the transaction directory (old program copy, candidate, package, backups) and, last, `transaction.json` (`staged`). Live files are unchanged. A failure removes the directory.
2. **Hand-over** (750 ms after the answer): the host drains and saves exactly as for `SIGTERM`/restart, then `exec`s the *old* program's copy as `mosdns update-guard --transaction <file>` — **the same process id**, so a service manager never sees the service stop.
3. **Guard** (old code, no sockets): `installing` → writes the package files and state → installs the candidate over the program (atomic rename) → `testing` → starts the candidate as its **child** (`MOSDNS_UPDATE_GUARD_TXN` set; the child asks to die with the guard, and exits at once if the guard has already gone) → polls the candidate's health (default 60 s; 3 consecutive `200 && ready && version == tag && applied_config_schema ≥ required`). Healthy → writes `verified` first, then stops the candidate, records `update/installed.json` and `exec`s the final program (same arguments, same process id). Not healthy, exited, or timed out → stops it and **rolls back**.
4. **Rollback** (idempotent): restores the configuration files and package state from the backup (existing files rewritten, files that did not exist removed), checks the saved program's sha256 and installs it, **then** writes `rolled_back` with the reason, then `exec`s the old program again (the program file is rewritten only when it is not already the old one). A config-only update (`kind "config"`) has no program swap and is otherwise identical.
5. **Recovery at every start** (before the configuration is loaded): any `installing`/`testing` transaction not belonging to the guard's own candidate is rolled back the same way and the old program is started; stale `staged` ones are closed; confirmed ones are cleaned up. A rollback that cannot complete leaves the state as it was and fails the start rather than running a mixed state.

Why this does not depend on `systemd`: the guard *is* the service's main process, the candidate is its child, and every ordinary failure (candidate crash, no start, unhealthy, timeout, pre-flight, write error) is handled by the guard within seconds without the main process ever exiting, so `RestartSec` never applies. Only if the guard itself is killed (`kill -9`, OOM) does the main process disappear; the candidate dies with it, the service manager starts the installed program after `RestartSec`, and the recovery above rolls back before the host runs. Power loss is the same: states are durable, so `installing`/`testing` are recognised after boot.

Interruption table: before `installing` nothing live has changed; during `installing` any prefix of the file writes is undone from the backup; the program swap is one rename; from `testing` on, the candidate is on trial and any interruption rolls back; `verified` is written only after the candidate proved healthy, so a kill after it leaves a consistent new installation.
