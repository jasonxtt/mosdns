## Observed capability contract

The following is the smallest contract actually observed on this host:

```text
resolve target:
  read_thread(reference) -> thread.id, thread.kind, thread metadata

send(reference, message):
  send_message_to_thread({threadId: reference.id, prompt: message})
  -> success with the same threadId

read(reference):
  read_thread({threadId: reference.id})
  -> latest completed user/assistant turns for that ChatGPT conversation

wait:
  no generic wait_threads support for kind=chatgpt was observed;
  polling read_thread with the same reference is the available mechanism

stable identity semantics:
  the user-provided /c/<id> reference, send result threadId, and read
  result thread.id were identical; read also preserved kind=chatgpt
```

Known limitation: the host exposes the ChatGPT conversation read/send path,
but the tested generic wait capability only accepts Codex threads. A future
controller must therefore use bounded polling or another officially exposed
ChatGPT-specific wait capability rather than call `wait_threads` blindly.
