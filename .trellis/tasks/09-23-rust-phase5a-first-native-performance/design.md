# Design — paired Go-only / Rust-native W1–W3 measurement

Status: in progress — Slice 0 reviewer PASS; prepare and review the Slice 1 official manifest before measurements. No official measurements have been run and no official manifest is frozen.

## Evidence model

Use the archived baseline's exact four YAML configs, three workload files, controlled upstream fixture and correctness oracle as immutable inputs. The Go-only and native binaries are independently built from frozen commits and passed to the existing `MOSDNS_BINARY` entrypoint. Each measured tuple is `(scenario, offered rate, repetition, implementation, manifest SHA)`; Go and Rust use the same tuple settings and distinct result directories. Neither the historical 4-CPU run manifest nor its results may be rewritten.

The existing runner starts `MOSDNS_BINARY start -c <config>`, supports smoke/pilot/official, collects SUT/fixture results, and verifies W2/W3 counters. Before editing, check current source support for release native-host CLI, fixed-rate sender, response classification, resource samples and cleanup. Extend only the smallest test-only surface needed for paired scheduling, per-run metadata and report aggregation. Do not add a generic benchmark platform or implementation-specific oracle. If any adapter normalizes dynamic DNS fields, document exactly which wire fields are ignored and why; never normalize rcode, answers, routes or cache behavior.

### W3 route-event evidence contract

The current per-upstream counters are not sufficient to establish a route sequence. For W3, run the three controlled route endpoints through one test-only fixture session with a shared append-only JSONL event journal and a single monotonically increasing `fixture_seq`. Each event records `fixture_seq`, `occurred_at`, `dns_id`, normalized `qname`, `qtype`, `qclass`, and `upstream`. The client ledger records `run_id`, `stage_id`, monotonic `request_seq`, `dns_id`, `case_id`, question tuple, `sent_at`/`finished_at`, and terminal outcome. Stage results record `fixture_seq_start`/`fixture_seq_end` barriers so events cannot leak between measured stages.

The first Go-only W3 VM smoke showed that the candidate rewrites DNS transaction IDs on its upstream legs: client ledger IDs were `41645`–`41647`, while fixture events recorded `0`/`1`; responses were correct. Therefore upstream DNS ID is diagnostic only and cannot be the client-to-fixture join key. Correlate a fixture event with the unique same-question client request whose `[sent_at, finished_at]` interval contains `occurred_at`, within the stage sequence barriers. The W3 sender still allows at most one in-flight request for a canonical `(qname,qtype,qclass)` tuple; the verifier rejects overlapping intervals or an event matching zero or multiple request intervals. Other question tuples remain concurrent. For each request, order its assigned events by the shared `fixture_seq` and require its exact expected path and leg count. This prevents events from one request being redistributed to a later repeated question. Continue allocating and quarantining client DNS IDs for response matching; record fixture-side IDs for diagnosis. Any ID rewrite is an expected transport detail, not a reason to weaken DNS response or route semantics. If timestamp correlation or single-flight causes sender shortfall at a required rate, that W3 point is invalid rather than silently lowering its offered rate. Freeze schema `fixture-event-v3-occurrence-time` and the correlation contract hash in the new manifest. Measure journal CPU, memory, and storage headroom in the v7 pilot; trace overflow or fixture saturation invalidates the point.

Test first with synthetic journals to reject missing, duplicate, forbidden, reversed, out-of-window, and unmatched legs, plus overlapping same-question requests even when their client IDs differ, rewritten upstream IDs, and event sequence regressions. Then run the same oracle against each real candidate's W3 smoke and official stages. Existing aggregate counters remain useful as a cross-check, but cannot substitute for the event oracle.

### Continuous overload and recovery session

Each measured scenario session starts one candidate and its fixture set once, then runs all stages without stopping either process: normal reference, common load, near-saturation, overload, and a terminal post-sequence health check at the exact normal-reference offered rate. Record the same SUT PID/start identity and fixture-session identity on every stage row. Each stage is rate-controlled and has its own counters, resource sample window, request ledger, and fixture sequence barriers; drain requests and record the barrier between stages without restarting or resetting state.

W2 cold remains an isolated fresh-process measurement. W2 warm starts a separate session, performs the explicit unmeasured prefill, and then runs its normal-reference→common→near-saturation→overload→health-check sequence against the warm set. W1 UDP/TCP and W3 use one session per implementation/repetition for their sequence. Every repetition starts fresh; only stages within that repetition share the same SUT PID.

The archived fixture's A answers carry a 30-second TTL, and the frozen cache config sets `lazy_cache_ttl: 0`; treat 30 seconds as the maximum age of each prefilled W2 cache entry. Record each key's prefill time and each measured response time, and freeze a safety margin from the pilot. A W2 warm stage is eligible for cache-hit claims only when every response is completed before its key's TTL deadline minus that margin. If the manifest selects independent prefilled stages, collect each measured stage from its own frozen per-stage path, carry its prefill/TTL failure reason into that observation, and retain an explicit indeterminate recovery assessment. Do not refill between same-process stages or change the frozen fixture/config to extend the TTL; that would change the recovery state or benchmark inputs.

During the non-official pilot, collect at least three stable normal-reference stage samples at the final same-rate health-check duration. For W2 warm, measure the full prefill-to-final-response span and verify it fits within each key's 30-second TTL minus the frozen safety margin. Freeze the sample minimum and maximum observed reference p95/p99 as the health-check ceilings. This VM pilot did not establish an objective overload point or a pre-frozen overload trigger. Therefore the manifest freezes `recovery_assessment_mode=indeterminate-no-overload-evidence`; even a same-PID, fully healthy final stage is only a post-sequence health check and never service-recovery proof in this task. Any future service-recovery claim needs a new manifest with an objective overload-evidence rule defined before measurement.

Mock boundary: the existing loopback fixtures are the only substitutes for upstream DNS and expose deterministic answers plus counters. Do not mock either candidate binary, DNS parsing/result behavior, or the on-VM CPU/resource path. Unit tests may use temporary JSON/config/result files and deterministic scheduler inputs for parser, pairing, manifest, and aggregation logic. Validate CPU affinity with the actual runner/helper/fixture process tree on the test VM; setting `HARNESS_CPU_SET` alone is not an affinity control.

The initial code audit found four test-tool gaps before candidate smoke: incomplete fixed-input/helper hash verification, descriptive-only harness affinity, an incomplete DNS response oracle, and aggregate-only W3 route counters. Slice 0 added test-first fixes for these gaps, plus same-process stages, sender/resource gates and paired result collection. Reviewer re-review found a further W3 evidence flaw: ordered tuple occurrences alone cannot prevent one request's duplicate fixture events from being assigned to a later repeated question. The v7 oracle timestamps each fixture event and assigns it to exactly one client request interval, then checks that request's exact route array; the live rewritten upstream DNS ID remains diagnostic. Re-review also established that the current rate ladder lacks a frozen objective overload trigger, so the manifest forces categorical indeterminate service-recovery status while retaining the final stage as a post-sequence health check. W2 independent-prefilled collection reads per-stage result files, propagates stage-prefill and lifecycle status, and preserves its indeterminate assessment. The v8 helper also emits that same categorical assessment with the failed health-check reason before returning a nonzero health-gate result, so a failing terminal check cannot erase the frozen interpretation. The new manifest freezes helper/schema/recovery assessment modes alongside candidate/input hashes and the stage plan.

## Preflight and freeze

On `ssh mosdns-rust`, use a task-owned directory on the disk-backed filesystem for build/result artifacts; `/tmp` may be a 2 GiB tmpfs. Verify architecture, toolchains, available cores/memory/disk, FD/cgroup/affinity, idle load, ports and correct cleanup. Run both binaries through the unchanged strict DNS/W2/W3 event smoke matrix. Pin helper version and ensure the same helper drives both processes. The runner's `HARNESS_CPU_SET` field is descriptive only: use an outer `taskset`/cpuset to pin the harness and fixture process tree, pin the SUT separately, then inspect the actual allowed CPU sets. A short non-official pilot determines offered-rate ladder and whether the generator, event journal, and loopback fixtures can sustain it; it also exercises one continuous stage sequence and establishes the reference noise band. Validate that failed sends, dropped scheduling slots, timer slip, trace loss, and fixture saturation are observable. Verify every manifest input hash, not only the manifest file and SUT binary. Freeze a **new** JSON manifest and hash before official samples, including the terminal health-check criteria, categorical indeterminate recovery mode, and event schema. Pilot rows remain labeled non-official.

On the 2-CPU VM the default credible setup is one pinned SUT core and one pinned generator/fixture core, with sequential Go and Rust runs; this measures comparable single-core service behavior, not multi-core scaling. An unpinned exploratory run may be retained separately but cannot serve as the capacity verdict. If helper/upstream CPU approaches saturation, scheduling slips, or machine load changes materially, invalidate the affected point; do not lower its QPS after viewing Rust results. A multi-core capacity claim waits for more isolated capacity.

## Official run and output

For each W1-UDP, W1-TCP, W2 and W3 scenario, run the frozen rate ladder with at least three repetitions and alternate Go-first/Rust-first order. Keep one SUT PID and fixture session alive across each same-process scenario's stages. W2 yields a separate cold fresh-process row and a warm sequence with explicit prefill; independent-prefilled mode stores and collects each stage separately and cannot support same-process recovery. W1 TCP retains the frozen fresh-connection-per-request policy. After each stage, validate DNS responses, W2 counter/TTL deltas, W3 event timestamps and exact per-request paths, sequence barriers, and process identity before considering performance data. Store environment, manifest hash, SUT/helper SHA, per-stage counters/latencies, same-PID/session identity, health-check result plus categorical recovery assessment, /proc CPU/RSS/FD samples, fixture event journal and logs. Retain invalid attempts with reason and no overwrite. Stop task-owned processes on error or interruption; do not touch other VM services.

Aggregate paired points by scenario and offered rate. Report per-run values plus median/range across repetitions; p99 interpretation must mention sample counts, especially at low QPS. Effective throughput is correct and within deadline per measured second, not all received packets. Report failures and offered/sent deltas beside latency. CPU/query denominator is correct-on-time count; an empty denominator is invalid, not zero. RSS must distinguish startup/stable/peak and note VM noise. For W2, show cold/warm hit and upstream deltas; for W3, index request intervals to event timestamps and show exact per-request route arrays. For the final same-rate stage, publish the health-check result and the frozen `indeterminate-no-overload-evidence` assessment; do not label it recovered. If instrumentation is missing or lossy, mark the affected point invalid; never infer a precise figure from aggregate counts or unrelated historical output.

## Decision and change controls

Only test/benchmark tooling, new task evidence and a bounded report under `docs/rust/` are in scope. Immutable `tests/phase5a-baseline/configs/**`, `workloads/**`, archived baseline evidence and Go/Rust product code stay untouched. If a product defect blocks a scenario, preserve its repro, pause that scene and route a separately reviewed implementation fix; afterwards rebuild, re-freeze and rerun both candidates. Comparator, config, timeout or method changes after seeing official results require a new manifest and full paired rerun.

Interpretation order: correctness gate → measurement validity → valid latency/effective-throughput/resource curves → uncertainty → optimization suggestion. The report explicitly labels all-feature, long-run stability, multi-core scaling and production behavior as unmeasured.
