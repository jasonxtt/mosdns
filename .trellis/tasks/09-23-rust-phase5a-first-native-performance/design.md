# Design — paired Go-only / Rust-native W1–W3 measurement

Status: in progress — Slice 0 pilot complete; scoped changes awaiting reviewer PASS. No official measurements have been run and no official manifest is frozen.

## Evidence model

Use the archived baseline's exact four YAML configs, three workload files, controlled upstream fixture and correctness oracle as immutable inputs. The Go-only and native binaries are independently built from frozen commits and passed to the existing `MOSDNS_BINARY` entrypoint. Each measured tuple is `(scenario, offered rate, repetition, implementation, manifest SHA)`; Go and Rust use the same tuple settings and distinct result directories. Neither the historical 4-CPU run manifest nor its results may be rewritten.

The existing runner starts `MOSDNS_BINARY start -c <config>`, supports smoke/pilot/official, collects SUT/fixture results, and verifies W2/W3 counters. Before editing, check current source support for release native-host CLI, fixed-rate sender, response classification, resource samples and cleanup. Extend only the smallest test-only surface needed for paired scheduling, per-run metadata and report aggregation. Do not add a generic benchmark platform or implementation-specific oracle. If any adapter normalizes dynamic DNS fields, document exactly which wire fields are ignored and why; never normalize rcode, answers, routes or cache behavior.

## Observable behavior slices and TDD boundary

The candidate-facing public interface is the real binary's `mosdns start -c <unchanged fixture YAML>` command and its loopback DNS UDP/TCP listener. The measurement-tool interfaces are the existing environment-variable contract of `scripts/run-phase5a-baseline.sh` (`MOSDNS_BINARY`, `SCENARIO`, `RUN_MODE`, result/manifest fields) and the helper's `run`, `verify-counters`, and `validate-binary` commands. Go and Rust internals are not test interfaces.

### W3 route-event evidence contract

The current per-upstream counters are not sufficient to establish a route sequence. For W3, run the three controlled route endpoints through one test-only fixture session with a shared append-only JSONL event journal and a single monotonically increasing `fixture_seq`. Each event records `fixture_seq`, `dns_id`, normalized `qname`, `qtype`, `qclass`, and `upstream`. The client ledger records `run_id`, `stage_id`, monotonic `request_seq`, `dns_id`, `case_id`, question tuple, send/result times, and terminal outcome. Stage results record `fixture_seq_start`/`fixture_seq_end` barriers so events cannot leak between measured stages.

The first Go-only W3 VM smoke showed that the candidate rewrites DNS transaction IDs on its upstream legs: client ledger IDs were `41645`–`41647`, while fixture events recorded `0`/`1`; responses were correct. Therefore upstream DNS ID is diagnostic only and cannot be the client-to-fixture join key. Correlate within the session/stage barriers by canonical `(qname,qtype,qclass)` and ordered occurrence. To make that mapping unambiguous, the W3 sender must allow at most one in-flight request for a given question tuple, independent of client DNS ID; the verifier checks the request intervals do not overlap. Other question tuples remain concurrent. Group that tuple's fixture events by the shared `fixture_seq`, then consume the exact expected route path for each corresponding client-ledger occurrence. This proves exact leg count and order because the same tuple cannot overlap, while preserving interleaving and load among different tuples. Continue allocating and quarantining client DNS IDs for response matching; record fixture-side IDs for diagnosis. Any ID rewrite is now an expected transport detail, not a reason to weaken DNS response or route semantics. If the single-flight rule creates sender shortfall at a required rate, that W3 point is invalid rather than silently lowering its offered rate. Freeze the event schema/correlation contract and hash in the new manifest before official runs. Measure journal CPU, memory, and storage headroom in the pilot; trace overflow or fixture saturation invalidates the point.

Test first with synthetic journals to reject missing, duplicate, forbidden, reversed, out-of-window, and unmatched legs, plus overlapping same-question requests even when their client IDs differ, rewritten upstream IDs, and event sequence regressions. Then run the same oracle against each real candidate's W3 smoke and official stages. Existing aggregate counters remain useful as a cross-check, but cannot substitute for the event oracle.

### Continuous overload and recovery session

Each measured scenario session starts one candidate and its fixture set once, then runs all stages without stopping either process: normal reference, common load, near-saturation, overload, and recovery at the exact normal-reference offered rate. Record the same SUT PID/start identity and fixture-session identity on every stage row. Each stage is rate-controlled and has its own counters, resource sample window, request ledger, and fixture sequence barriers; drain requests and record the barrier between stages without restarting or resetting state.

W2 cold remains an isolated fresh-process measurement. W2 warm starts a separate session, performs the explicit unmeasured prefill, and then runs its normal-reference→common→near-saturation→overload→recovery sequence against the warm set. W1 UDP/TCP and W3 use one session per implementation/repetition for their sequence. Every repetition starts fresh; only stages within that repetition share the same SUT PID.

The archived fixture's A answers carry a 30-second TTL, and the frozen cache config sets `lazy_cache_ttl: 0`; treat 30 seconds as the maximum age of each prefilled W2 cache entry. Record each key's prefill time and each measured response time, and freeze a safety margin from the pilot. The W2 warm sequence is eligible for cache-hit and recovery claims only when every response is completed before its key's TTL deadline minus that margin. If the full sequence cannot fit, preserve the independent warm points by using a fresh session and explicit prefill per measured stage, but label W2 same-process warm recovery indeterminate. Do not refill between stages or change the frozen fixture/config to extend the TTL; that would change the recovery state or benchmark inputs.

During the non-official pilot, collect at least three stable normal-reference stage samples at the candidate recovery rate and duration. For W2 warm, also measure the full prefill-to-final-response span and verify it fits within each key's 30-second TTL minus the frozen safety margin; if not, use independent prefilled warm stages and mark same-process warm recovery indeterminate. Freeze the recovery duration, minimum sample count, and the maximum observed reference p95/p99 values as the latency ceiling. A recovery stage is service-recovered only if it uses the same SUT PID and fixture session, every scheduled query is correct-on-time, late/wrong/protocol/transport/timeout/sender-shortfall counts are zero, and its p95 and p99 do not exceed those frozen ceilings. If the reference band or required sample count cannot be established, report recovery as indeterminate. RSS/FD/CPU after overload remain separate diagnostics; this short task does not claim long-run resource recovery.

Mock boundary: the existing loopback fixtures are the only substitutes for upstream DNS and expose deterministic answers plus counters. Do not mock either candidate binary, DNS parsing/result behavior, or the on-VM CPU/resource path. Unit tests may use temporary JSON/config/result files and deterministic scheduler inputs for parser, pairing, manifest, and aggregation logic. Validate CPU affinity with the actual runner/helper/fixture process tree on the test VM; setting `HARNESS_CPU_SET` alone is not an affinity control.

The initial code audit found four test-tool gaps to close before candidate smoke. Official mode checked the manifest SHA-256 and recorded the SUT identity, but did not verify every config/workload/helper input hash. The runner recorded `HARNESS_CPU_SET` without applying it. `responseMatches` checked ID, a single question's name/type, expected rcode, and a matching A answer, but did not enforce the response bit, opcode, question class, truncation, or exact complete answer set. Finally, `verifyRoutingCounters` only required positive aggregate counts for required legs, so it could not detect duplicate legs or reversed order. These gaps are being addressed with test-first strict DNS and W3 event oracles, per-input/helper hash verification, a continuous-stage runner mode, and verified affinity for the generator/fixtures. Observed VM affinity is recorded for the actual runner, fixtures, and SUT. The first Go-only W3 smoke also disproved the assumption that upstream fixture DNS IDs preserve the client request ID; the correlation contract is now ordered canonical question occurrences with one in-flight request per tuple, while upstream IDs remain diagnostic. The new manifest must identify the runner/helper source and binary hashes, W3 event/correlation schema, stage sequence, and recovery criterion alongside both SUTs and all seven corpus hashes.

## Preflight and freeze

On `ssh mosdns-rust`, use a task-owned directory on the disk-backed filesystem for build/result artifacts; `/tmp` may be a 2 GiB tmpfs. Verify architecture, toolchains, available cores/memory/disk, FD/cgroup/affinity, idle load, ports and correct cleanup. Run both binaries through the unchanged strict DNS/W2/W3 event smoke matrix. Pin helper version and ensure the same helper drives both processes. The runner's `HARNESS_CPU_SET` field is descriptive only: use an outer `taskset`/cpuset to pin the harness and fixture process tree, pin the SUT separately, then inspect the actual allowed CPU sets. A short non-official pilot determines offered-rate ladder and whether the generator, event journal, and loopback fixtures can sustain it; it also exercises one continuous stage sequence and establishes the reference noise band. Validate that failed sends, dropped scheduling slots, timer slip, trace loss, and fixture saturation are observable. Verify every manifest input hash, not only the manifest file and SUT binary. Freeze a **new** JSON manifest and hash before official samples, including the recovery criterion and event schema. Pilot rows remain labeled non-official.

On the 2-CPU VM the default credible setup is one pinned SUT core and one pinned generator/fixture core, with sequential Go and Rust runs; this measures comparable single-core service behavior, not multi-core scaling. An unpinned exploratory run may be retained separately but cannot serve as the capacity verdict. If helper/upstream CPU approaches saturation, scheduling slips, or machine load changes materially, invalidate the affected point; do not lower its QPS after viewing Rust results. A multi-core capacity claim waits for more isolated capacity.

## Official run and output

For each W1-UDP, W1-TCP, W2 and W3 scenario, run the frozen rate ladder with at least three repetitions and alternate Go-first/Rust-first order. Keep one SUT PID and fixture session alive across each scenario's staged sequence. W2 yields a separate cold fresh-process row and a warm sequence with explicit prefill before its normal-reference→overload→recovery stages. W1 TCP retains the frozen fresh-connection-per-request policy. After each stage, validate DNS responses, W2 counter deltas, W3 per-request event paths, event-sequence barriers, and process identity before considering performance data. Store environment, manifest hash, SUT/helper SHA, per-stage counters/latencies, same-PID/session identity, recovery reference and result, /proc CPU/RSS/FD samples, fixture event journal and logs. Retain invalid attempts with reason and no overwrite. Stop task-owned processes on error or interruption; do not touch other VM services.

Aggregate paired points by scenario and offered rate. Report per-run values plus median/range across repetitions; p99 interpretation must mention sample counts, especially at low QPS. Effective throughput is correct and within deadline per measured second, not all received packets. Report failures and offered/sent deltas beside latency. CPU/query denominator is correct-on-time count; an empty denominator is invalid, not zero. RSS must distinguish startup/stable/peak and note VM noise. For W2, show cold/warm hit and upstream deltas; for W3, index the request ledger to the fixture event journal and show exact per-request route arrays. For recovery, show that the normal-reference, overload, and recovery rows share one PID/session, publish the frozen ceilings and sample count, and label the result recovered/not recovered/indeterminate. Overload and recovery stages are separate. If instrumentation is missing or lossy, mark the affected point invalid; never infer a precise figure from aggregate counts or unrelated historical output.

## Decision and change controls

Only test/benchmark tooling, new task evidence and a bounded report under `docs/rust/` are in scope. Immutable `tests/phase5a-baseline/configs/**`, `workloads/**`, archived baseline evidence and Go/Rust product code stay untouched. If a product defect blocks a scenario, preserve its repro, pause that scene and route a separately reviewed implementation fix; afterwards rebuild, re-freeze and rerun both candidates. Comparator, config, timeout or method changes after seeing official results require a new manifest and full paired rerun.

Interpretation order: correctness gate → measurement validity → valid latency/effective-throughput/resource curves → uncertainty → optimization suggestion. The report explicitly labels all-feature, long-run stability, multi-core scaling and production behavior as unmeasured.
